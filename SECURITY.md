# Security

CodeConnect sits between an AI agent and your machine, so it is worth being precise about what it can do and what it protects.

## Reporting a vulnerability

Please **do not** open a public issue for a security problem. Use GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) on this repository.

Include what you did, what happened, and what you expected. A proof of concept helps. This is a personal project, so expect a first response in days rather than hours.

## What the software can do

- **`ccd`** runs as your user under launchd on macOS, or as a systemd user unit on Linux. It reads what each run's agent host and Codex's app server report, and sends a run's answers and messages back through them.
- **Hosted sessions message each other: CodeConnect Messages.** Every session CodeConnect starts has one MCP server of CodeConnect's own, `codeconnect`, whose `msg_send` tool asks `ccd` to give another hosted session a message, which the receiving computer's `ccd` keeps until that session reads it with `msg_read`. The sender `ccd` records is the session the tool was started for, never anything the session or the message says; a program running as the same OS user could still pose as any of your sessions, which is inside the trust this design gives your own computers. Who can send is the boundary: a session on this computer, through this computer's `ccd` alone (with Tailscale or with none, except on a tagged computer, which takes part in no messages, its own sessions' included; with no Tailscale reading, this computer's addresses read `<run id>@this.computer`); or a session on another computer, carried by that computer's `ccd` to this one's on its WebSocket port over Tailscale. The receiving `ccd` serves only connections that its own `tailscale status` says come from a computer of the same Tailscale user that is not tagged, and it names the sender by that computer's name, never by anything the request claims. So any program on any such device of the same Tailscale user can send your sessions a message, with no further credential. Such a connection asks one thing (the list of sessions, one message, or where a message it sent now stands, which only the computer the message went to may say) and gets nothing else: no event log, no approvals. Each session asks for CodeConnect's tools as its own mode and its folder's trust say: Codex asks before each `msg_send` until its card is answered "Allow for this session", and lists and reads without asking; in a folder the person trusts, a Claude session lists and reads without asking and asks before each send, as its permission mode says; a folder not trusted asks before every one of CodeConnect's tools. Either question reaches the phone like any other card. What the receiving session then does is governed by its own permission mode and by one switch per computer, on unless set off (`codeconnect msg-act on|off`; an `off` written before is kept): on, `msg_read` tells it to treat a message as a teammate's request within its own permissions, never as your approval and never to change settings; off, to show the message to you and not act on it. So, on, a session does what a message asks as far as its mode lets it act unasked: a Claude session in Ask before edits asks you before each edit and command; in Accept edits it edits unasked and asks before commands; in Bypass permissions, like a Codex session in Full Access, it asks you nothing; a Codex session in Default edits files and runs commands inside its workspace unasked, and asks before anything that needs more (writing outside it, or the network). The switch is guidance to the model, not enforcement: a session that reads hostile content can still pass instructions on to another one, on any of your computers. Claude Code's own session messaging (its ListAgents and SendMessage) is outside CodeConnect: it raises no card, the act-on-messages switch does not apply to it, and the apps show none of its messages, only the work a session does after one.
- **No system service is involved.** CodeConnect does not enable Remote Login or anything like it, and does not ask you to: `ccd` is a launchd job (a systemd user unit on Linux) running as your user, and everything the phone reaches on your computer goes through it. The phone does reach two things directly that are not on your computer — Apple, and CodeConnect's push relay — for App Attest and the push-credential lifecycle; neither is a service on your machine.

## Trust boundaries

- **Local by default, with documented exceptions.** The daemon binds to your Tailscale interface and loopback. There is no account. CodeConnect keeps sessions and approvals between your devices; default relay-backed push is one documented external exception. The coding agents themselves send your conversation to the AI providers they use, normally Anthropic, OpenAI and Google (Antigravity), outside CodeConnect. There is no app or product telemetry, though the relay exposes aggregate operational metrics. The relay's push route accepts only the fixed content-free notification fields named in the privacy policy, while its separate enrollment, status, and assertion routes accept only the documented App Attest and credential fields; relay-backed notifications pass through it on their way to Apple.
- **The phone is a client, not an authority.** It holds a per-device token issued at pairing, stored hashed. Tokens are listed with `codeconnect devices` and revoked with `codeconnect revoke <device>` — revocation closes open connections rather than waiting for the next reconnect.
- **Your own Tailscale devices pair without a code.** A device of this computer's own Tailscale user, not tagged, with this computer not tagged either, is given a device token on a `hello` that carries no credential; the same rule decides which computers may send Mail. That trust is the whole device's: every account on a trusted computer and every app on a trusted phone gets in, and there is no switch to require a code instead. Revoking a device keeps its whole Tailscale device out until `codeconnect unblock` lets it back in with the token it already holds: it cannot sign in, it can no longer exchange your agents' messages in either direction, and no device is told about it. Anything Tailscale does not vouch for (another user's device shared into your tailnet, a tagged device, a phone off Tailscale, this computer's own loopback) still needs a code.
- **Pairing codes are single-use and expire in 5 minutes.**
- **Push notifications are a doorbell, and only a doorbell.** With its own APNs provider key configured the daemon sends notifications directly to Apple; otherwise, when relay-backed push is enabled, it sends CodeConnect's push relay a content-free request — a kind, a count, the token, its environment and its credential — and the relay builds a generic notification titled `CodeConnect`; with neither, the sender is an inert logging stub. `hello_ack` capabilities tell the phone which mode it is talking to. What crosses Apple's servers in the **direct** path is deliberately austere: the **project** a run is working in (the last component of its working directory), one of two canned sentences, and a count of how many runs are holding a decision (under coalescing that count *replaces* the sentence rather than joining it). In the **relay** path even the project label stays on the Mac. It carries no tool name and no risk tier, no session uid, no request id and no routing token — nothing that could be reversed into a command or left pointing at a decision. It does carry one word, `approval`, which is what sends a tap to the decision list without naming anything — a notification rings only while a decision the phone can answer is waiting — and a fixed collapse id — the constant string `codeconnect`, identical for every device and every run — so that a later doorbell replaces an earlier one instead of racing it. (A *test* notification, which the user asks for explicitly, is a separate fixed payload carrying a `codeconnect_test` marker so the phone can banner it.) Apple necessarily sees the device token in the request path, and repeated project titles are of course comparable to each other; the claim here is about the JSON, not anonymity. Nothing an agent wrote ever rides a push: a body is either one of two canned sentences, chosen by whether the one decision waiting is a question, or — when several runs are holding decisions — a count, never the agent's message, so no command text, no diffs and no paths leave the tailnet. The app reconnects and asks the event log what is true. A paired phone can also request one **test** notification (rate-limited per device, refused for the bootstrap token) to prove the chain end to end.
- **Approvals are gated on evidence.** An answer from the phone carries the request ID and a hash of the exact text that was displayed. A Claude approval is answered only through the agent host Claude runs under, keyed by its tool-call id, and an Antigravity approval only through the agent host agy runs under, keyed by its request; nothing is typed into a permission prompt. If that call has already been answered, has run, or is not held, the answer is refused rather than applied to something else.

## What a stolen phone token can do

State this plainly, because it is wider than "it can approve things".

A valid device token can:

- **Read everything.** Every session and every event the daemon has filed, plus Git diffs on demand. Command output routinely contains secrets an agent printed, so treat this as read access to anything your agents have seen.
- **Answer live approvals**, once it has the displayed text to hash.
- **Submit arbitrary text to a session.** Against an agent running in a permissive mode, that is functionally close to command execution.
- **Start an agent in any folder.** From protocol minor 28 a paired device may start a session in a folder it names, with a first message of its choosing or none, and from minor 30 it may browse this computer's folders and make new ones to choose from. The static bootstrap token may do none of this.
- **Switch a Claude run CodeConnect started to a mode that asks nothing.** From protocol minor 40 a client may turn on Claude Code's Bypass permissions on a Claude run started from the app, once the app has asked the person to confirm it; the daemon refuses the change unless the call says it was confirmed. That says what the app did, not who you are: any paired connection, the bootstrap token included, can send a confirmed change. From then on that run's claude edits files and runs commands without asking, until the mode is changed back or its process ends; a new process starts in your own default mode. A run in Ask before edits, Accept edits or Plan keeps that mode when its process has to be started again; a run in a mode the app does not offer starts again in your own default mode. To make that switch possible, every run started from the app starts with Claude Code's own guard for the mode set, so if your own Claude Code settings make `bypassPermissions` your default mode, a run started from the app starts in it without the app's confirmation, as when you run claude directly; the app shows the run's mode from its first turn. A project's settings cannot do this: Claude Code drops a default mode that asks less from settings committed to the project.
- **Switch a Codex run CodeConnect started to Full Access.** From protocol minor 43 a client may turn on Codex's Full Access (approvals never, no sandbox) on a Codex run started from the app, once the app has asked the person to confirm it; the daemon refuses the change unless the call says it was confirmed, and, as for Claude's, any paired connection, the bootstrap token included, can send a confirmed change. From then on that run's Codex runs commands and edits files without asking, outside the project's folder and with network access, until the mode is changed back or its Codex has to be started again, which gives it Default's approval and sandbox; a restart of CodeConnect's daemon, which reconnects to the same Codex, keeps it.
- **Act on a Codex run with the authority it was started with, or the one an app set.** A Codex run started from the app starts in Codex's preset Default, `on-request` approvals with a `workspace-write` sandbox, and a trusted project's own approval policy and sandbox never replace it; a run whose Codex is started again is resumed with the same two, or in Read Only or Plan when it was in one of them, never in Full Access, and one the daemon reconnects to after its own restart with the approval and sandbox Codex last named for it; a run in Plan is set to Plan again after every resume before it takes a message. A run never gains permissions by restarting, beyond the settings Codex last reported. From protocol minor 43 an app may set the run to Read Only, Plan or, confirmed, Full Access (above).
- **Destroy history, one run at a time, and irreversibly.** From protocol minor 7 a client may send `delete_session`, which removes that run's row and every event and answer filed under it. There is no undo and no archive. It is refused unless the run has ended (`exited` or `failed`), and refused while an approval of the run is still open. It does not reach Claude Code's own transcripts under `~/.claude/projects`, so the conversations themselves survive and remain resumable. What is lost is CodeConnect's record: the timeline, the approvals and what was decided.

The daemon's own protocol gives it none of the following: it cannot use the local IPC administration socket or delete a running *hosted* session's record. It can stop a run's turn (`interrupt`), and end a run CodeConnect started, Claude's, Codex's or Antigravity's (`stop_run`, from protocol minor 35), never one it did not start.

**What `revoke` reaches, and what it still may not.** It withdraws the device token, the credential the daemon mints when a device pairs — and, because an earlier release also appended a phone's key to `~/.ssh/authorized_keys`, it now sweeps that file as well, as the daemon already does at startup. The sweep is unconditional and takes the whole file rather than the named device's entries, so re-running `codeconnect revoke <device>` on a phone that is already revoked is the operator's retry for a sweep that failed earlier. It stays best-effort: it removes a marker comment and the bare three-field `ssh-ed25519` line directly beneath it carrying the same tag, both lines or neither, and it removes nothing at all when there is no absolute `$HOME`, when the file cannot be read, when it cannot be rewritten, or when the file changed underneath the sweep — that last one is the sweep declining rather than failing, because a file another program has just rewritten is not one to overwrite with a copy read before that write, and it retries before it gives up. Each of those is a warning in the daemon log rather than a revocation that fails. A key line without its marker above it is left alone on purpose, whatever its comment field says, because who wrote a line is not recorded in the file and the daemon will not claim one it cannot prove it wrote. So a phone can still hold SSH access that revoking its token did not take back: by one of those paths, or by a key living outside `$HOME/.ssh/authorized_keys` or outside that shape. Check with `grep -n codeconnect: ~/.ssh/authorized_keys` and delete both lines of any pair it prints — a pair still in that output is one no sweep has reached.

**The static bootstrap token is weaker than a device token.** It is a permanent global credential, stored in plaintext because it has to be readable before pairing exists, it cannot be revoked individually, and connections already open with it deliberately survive deletion of the file. Pair a device, then delete it. It exists to bootstrap the first pairing, not to be a long-lived credential.

## What it does not protect against

- **An agent you have already told to skip permissions.** CodeConnect mirrors Claude Code's own prompts; it cannot gate what Claude Code never asks about.
- **Anyone with access to your unlocked Mac.** The daemon's socket and database are protected by file permissions, not by a second factor.
- **Transcripts are sensitive.** Transcripts can contain secrets an agent printed to stdout. They are stored unencrypted in `~/.codeconnect` under your user account, which is the same protection your shell history has.

## Transport

`wss://` wherever a certificate for a name that reaches this listener can be had — one dropped in `~/.codeconnect/tls/` by hand, or issued by `tailscale cert` when your tailnet has HTTPS certificates enabled. Whether `ws://` is admitted is settled separately: per listener, at startup, from that listener's own address. Unasked, it is admitted on loopback and on this Mac's own Tailscale address; `"ws_allow_plaintext": true` extends it to a local-network address the operator names in `ws_bind`. Any other address serves TLS or turns every connection away. Both schemes require a credential — a device token, or the static bootstrap token described above, which authenticates just as well and is exactly why it should be deleted once a device is paired.

**The QR carries a name where a name would reach this daemon, and the bind address where it would not.** A certificate's SAN is a DNS name and cannot validate against a bare tailnet IP, which is why a name is preferred wherever one is carried at all — and why it goes on being carried when no certificate could be obtained: the name survives a Tailscale IP change, and it is what the phone will need once one is. The QR falls back to the bind's own address in every case where a name would send a phone elsewhere or is not there to carry — a loopback bind, `tls` off, no MagicDNS name available, a name that resolves to some other address, or a name nothing confirmed with no certificate behind it. [`mac/README.md`](mac/README.md#tls) has each case.

**Plaintext fails closed, and the one key that opens it is bounded.** Four rules settle it per listener, at startup, before any connection reaches the credential exchange:

1. **Unasked, plaintext is admitted only where it is private already:** on loopback, or on this computer's own Tailscale address, where WireGuard encrypts the path before it touches a network. A listener on any other address — an explicit `ws_bind` onto a LAN, say — serves TLS or nothing, because the credential itself would otherwise cross the network readable.
2. **`"ws_allow_plaintext": true` softens that, and only for a local address:** private IPv4, IPv4 link-local, IPv6 unique-local (`fc00::/7`) or IPv6 link-local (`fe80::/10`). That is the whole of what an operator is in a position to vouch for, and the LAN bind above is the case it exists for. Anywhere rule 1 already admits plaintext the key changes nothing at all. The address weighed is the **listener's own**, read once at bind time and never guessed per connection from where a peer claims to be — so none of this bounds who may connect. A listener on `192.168.1.20` with the key set answers anything that can route a packet to it, and the credential that admits a phone crosses that network readable, so whatever can watch those bytes has it too — and what it then has is everything a stolen phone token has: the whole event log, the approval path, and starting agents in any folder. A connection admitted by this key is told so: it is advertised `private_transport: false`, and the phone's pairing screen says the connection is not encrypted, because vouching for a network is a different statement from the bytes on it being unreadable.
3. **It is refused on the wildcard address and on a public one.** `0.0.0.0` and `::` put the bearer token on every interface this computer has, including the ones nobody can enumerate in advance; plaintext on a public address is private on no hop of the way. Set on either, the key is logged as refused and the listener still serves TLS or nothing. An address the daemon could not check against its own tailnet — because it found no tailnet address at startup: Tailscale not found, not up, or too slow to answer — is never called public: unasked, it is refused and told to restart rather than to move, since it may be the tailnet address the operator meant. With the key set that outcome survives for the IPv4 half of a tailnet and not the IPv6 half, because Tailscale allocates IPv4 out of `100.64.0.0/10`, which rule 2 does not cover, and IPv6 out of `fd7a:115c:a1e0::/48`, which sits inside the `fc00::/7` rule 2 does. So an unconfirmed Tailscale IPv6 bind is honoured and serves plaintext — on the operator's word, not on anything this daemon confirmed.
4. **`tls_required` wins.** It is the stronger, opposite statement, and the opt-in never quietly undoes it: honouring an exception to it would announce plaintext the admission gate then refuses.
