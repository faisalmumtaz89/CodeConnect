# Security

CodeConnect sits between an AI agent and your machine, so it is worth being precise about what it can do and what it protects.

## Reporting a vulnerability

Please **do not** open a public issue for a security problem. Use GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) on this repository.

Include what you did, what happened, and what you expected. A proof of concept helps. This is a personal project, so expect a first response in days rather than hours.

## What the software can do

- **`ccd`** runs as your user under launchd. It reads Claude Code's hook payloads and session transcripts, and it can write keystrokes into a tmux pane you started with `codeconnect`.
- **The live terminal** attaches a paired device to a hosted session's tmux pane over the connection it is already authenticated on. There is no second transport and no second credential.
- **No system service is involved.** CodeConnect does not enable Remote Login or anything like it, and does not ask you to: `ccd` is a launchd job running as your user, and everything the phone reaches on your Mac goes through it. The phone does reach two things directly that are not on your Mac — Apple, and CodeConnect's push relay — for App Attest and the push-credential lifecycle; neither is a service on your machine.

## Trust boundaries

- **Local by default, with one documented exception.** The daemon binds to your Tailscale interface and loopback. There is no account. Sessions, terminals, and approvals remain between your devices; default relay-backed push is the documented external exception. There is no app or product telemetry, though the relay exposes aggregate operational metrics. The relay's push route accepts only the fixed content-free notification fields named in the privacy policy, while its separate enrollment, status, and assertion routes accept only the documented App Attest and credential fields; relay-backed notifications pass through it on their way to Apple.
- **The phone is a client, not an authority.** It holds a per-device token issued at pairing, stored hashed. Tokens are listed with `codeconnect devices` and revoked with `codeconnect revoke <device>` — revocation closes open connections rather than waiting for the next reconnect.
- **Pairing codes are single-use and expire in 5 minutes.**
- **Push notifications are a doorbell, and only a doorbell.** With its own APNs provider key configured the daemon sends notifications directly to Apple; otherwise, when relay-backed push is enabled, it sends CodeConnect's push relay a content-free request — a kind, a count, the token, its environment and its credential — and the relay builds a generic notification titled `CodeConnect`; with neither, the sender is an inert logging stub. `hello_ack` capabilities tell the phone which mode it is talking to. What crosses Apple's servers in the **direct** path is deliberately austere: the **project** a run is working in (the last component of its working directory), one of four canned sentences, and a count of how many runs are holding a decision (under coalescing that count *replaces* the sentence rather than joining it). In the **relay** path even the project label stays on the Mac. It carries no tool name and no risk tier, no session uid, no request id and no routing token — nothing that could be reversed into a command or left pointing at a decision. It does carry one word saying which of four kinds rang, which is what lets a tap choose between the decision list and the fleet without naming anything, and a fixed collapse id — the constant string `codeconnect`, identical for every device and every run — so that a later doorbell replaces an earlier one instead of racing it. (A *test* notification, which the user asks for explicitly, is a separate fixed payload carrying a `codeconnect_test` marker so the phone can banner it.) Apple necessarily sees the device token in the request path, and repeated project titles are of course comparable to each other; the claim here is about the JSON, not anonymity. Nothing an agent wrote ever rides a push: a body is either one of four canned sentences chosen by the hook's *type*, or — when several runs are holding decisions — a count, never the agent's message, so no command text, no diffs and no paths leave the tailnet. The app reconnects and asks the event log what is true. A paired phone can also request one **test** notification (rate-limited per device, refused for the bootstrap token) to prove the chain end to end.
- **Approvals are gated on evidence.** An answer from the phone carries the request ID and a hash of the exact text that was displayed. It is also bound to a prompt *generation* and a fingerprint of the prompt block as it appeared on screen, both re-checked against the **visible pane** immediately before a keystroke is sent. If the prompt has changed, or if identity cannot be established at all, the answer is refused rather than applied to something else.

## What a stolen phone token can do

State this plainly, because it is wider than "it can approve things".

A valid device token can:

- **Read everything.** Every session, every event, every transcript line the daemon has ingested, plus pane snapshots and Git diffs on demand. Terminal output routinely contains secrets an agent printed, so treat this as read access to anything your agents have seen.
- **Answer live approvals**, once it has the displayed text to hash.
- **Open a live terminal on a hosted session.** From protocol minor 13 the Terminal tab rides this same connection: a paired device attaches to the session's tmux pane and types into it directly. That is an interactive shell on your Mac — not "functionally close" to one. The carrier speaks tmux control mode, so the phone's keystrokes are delivered — as data, never as tmux control-protocol commands — to exactly the pane it is shown, addressed by a `session:window.pane` target so a pane moved out of the session fails closed rather than carrying input elsewhere. The phone cannot, by protocol, switch the client into another session or kill the server (though the shell it is typing into can of course run `tmux`, as any shell can). A phone-side resize never shrinks a human sitting at the Mac, and detaching — or revoking the device — leaves the session running untouched. The static bootstrap token is refused this capability entirely, and so is any connection whose bytes are not private in transit: the terminal needs TLS, loopback, or this Mac's own tailnet address, and is **not** offered over the cleartext LAN that `ws_allow_plaintext` opens (see [Transport](#transport)). One terminal per session, and a later attach **takes it over** rather than being refused: the terminal that was open is closed with code `superseded` and the newcomer streams. That is what lets a phone whose socket died without a FIN reattach to its own session instead of being locked out by a lease nothing is holding — and it means a second paired device can take a terminal away from the first. Every device that can open one already has shell-equivalent authority, so this grants nothing new; it is visible rather than silent, which is why the displaced device is told which ending it was.
- **Submit arbitrary text to a session.** Against an agent running in a permissive mode, that is functionally close to command execution even without the terminal.
- **Destroy history, one run at a time, and irreversibly.** From protocol minor 7 a client may send `delete_session`, which removes that run's row and every event, answer and cursor filed under it. There is no undo and no archive. For a run CodeConnect **hosts** (spawned by `codeconnect claude`), it is refused unless the lifecycle is `exited`, and refused for any run the daemon still holds a supervisor or an open approval for. For an **adopted** run — hooks arrived but CodeConnect never launched it, so no probe can ever prove it ended — it is accepted at any lifecycle: the honest contract is "the daemon cannot say; you may remove it", and removal also stops observation of that conversation until a new session start re-adopts it. Neither case reaches Claude Code's own transcripts under `~/.claude/projects`, so the conversations themselves survive and remain resumable. What is lost is CodeConnect's record: the timeline, the approvals and what was decided.

The daemon's own protocol gives it none of the following: it cannot use the local IPC administration socket, start or kill sessions, or delete a running *hosted* session's record. **But a live terminal moots that list.** A terminal is a real user-level shell in the session's pane, and a shell can run `codeconnect` itself, reach the IPC socket over the filesystem, and start or kill tmux sessions — everything above, by hand, with your account's authority. The protocol boundaries constrain the *messages* a token can send; they do not constrain a shell the token opened. This is the whole reason a terminal is gated to paired devices only and refused to the bootstrap token, and the reason `codeconnect revoke` is the switch to reach for first.

**What `revoke` reaches, and what it still may not.** It withdraws the device token, the credential the daemon mints when a device pairs — and, because an earlier release also appended a phone's key to `~/.ssh/authorized_keys`, it now sweeps that file as well, as the daemon already does at startup. The sweep is unconditional and takes the whole file rather than the named device's entries, so re-running `codeconnect revoke <device>` on a phone that is already revoked is the operator's retry for a sweep that failed earlier. It stays best-effort: it removes a marker comment and the bare three-field `ssh-ed25519` line directly beneath it carrying the same tag, both lines or neither, and it removes nothing at all when there is no absolute `$HOME`, when the file cannot be read, when it cannot be rewritten, or when the file changed underneath the sweep — that last one is the sweep declining rather than failing, because a file another program has just rewritten is not one to overwrite with a copy read before that write, and it retries before it gives up. Each of those is a warning in the daemon log rather than a revocation that fails. A key line without its marker above it is left alone on purpose, whatever its comment field says, because who wrote a line is not recorded in the file and the daemon will not claim one it cannot prove it wrote. So a phone can still hold SSH access that revoking its token did not take back: by one of those paths, or by a key living outside `$HOME/.ssh/authorized_keys` or outside that shape. Check with `grep -n codeconnect: ~/.ssh/authorized_keys` and delete both lines of any pair it prints — a pair still in that output is one no sweep has reached.

**The static bootstrap token is weaker than a device token.** It is a permanent global credential, stored in plaintext because it has to be readable before pairing exists, it cannot be revoked individually, and connections already open with it deliberately survive deletion of the file. Pair a device, then delete it. It exists to bootstrap the first pairing, not to be a long-lived credential.

## What it does not protect against

- **An agent you have already told to skip permissions.** CodeConnect mirrors Claude Code's own prompts; it cannot gate what Claude Code never asks about.
- **Anyone with access to your unlocked Mac.** The daemon's socket and database are protected by file permissions, not by a second factor.
- **Same-user tmux state is trusted.** A terminal resolves which session a `session_uid` names by a `CODECONNECT_SESSION_UID` stamp tmux keeps on the session, read from the shared `-L codeconnect` server. That stamp is a routing tag that tells honest session-name reuse apart — not a secret and not an ownership credential. A process running as this macOS user can read or change it, or create a session carrying another run's uid, and so redirect a terminal attach to a pane it controls. But such a process can already read and inject into every live pane on that server directly (`tmux send-keys`, `pipe-pane`), reach the owner-only IPC socket, and read the database — so the stamp grants it nothing it does not already hold. Preventing it would require a trust boundary below the user account, which is out of scope for the same reason the rest of this section is. Tailnet access alone does not grant it, the bootstrap token cannot open terminals, and a paired device that can is deliberately granted shell-equivalent authority. Where an honest session is genuinely live a duplicate stamp is refused as an identity mismatch rather than silently disambiguated, and every attach is pinned to the tmux server epoch and the client's own pid before a byte flows.
- **Terminal content is sensitive.** Transcripts and pane snapshots can contain secrets an agent printed to stdout. They are stored unencrypted in `~/.codeconnect` under your user account, which is the same protection your shell history has.

## Transport

`wss://` wherever a certificate for a name that reaches this listener can be had — one dropped in `~/.codeconnect/tls/` by hand, or issued by `tailscale cert` when your tailnet has HTTPS certificates enabled. Whether `ws://` is admitted is settled separately: per listener, at startup, from that listener's own address. Unasked, it is admitted on loopback and on this Mac's own Tailscale address; `"ws_allow_plaintext": true` extends it to a local-network address the operator names in `ws_bind`. Any other address serves TLS or turns every connection away. Both schemes require a credential — a device token, or the static bootstrap token described above, which authenticates just as well and is exactly why it should be deleted once a device is paired.

**The QR carries a name where a name would reach this daemon, and the bind address where it would not.** A certificate's SAN is a DNS name and cannot validate against a bare tailnet IP, which is why a name is preferred wherever one is carried at all — and why it goes on being carried when no certificate could be obtained: the name survives a Tailscale IP change, and it is what the phone will need once one is. The QR falls back to the bind's own address in every case where a name would send a phone elsewhere or is not there to carry — a loopback bind, `tls` off, no MagicDNS name available, a name that resolves to some other address, or a name nothing confirmed with no certificate behind it. [`mac/README.md`](mac/README.md#tls) has each case.

**Plaintext fails closed, and the one key that opens it is bounded.** Four rules settle it per listener, at startup, before any connection reaches the credential exchange:

1. **Unasked, plaintext is admitted only where it is private already:** on loopback, or on this Mac's own Tailscale address, where WireGuard encrypts the path before it touches a network. A listener on any other address — an explicit `ws_bind` onto a LAN, say — serves TLS or nothing, because the credential itself would otherwise cross the network readable.
2. **`"ws_allow_plaintext": true` softens that, and only for a local address:** private IPv4, IPv4 link-local, IPv6 unique-local (`fc00::/7`) or IPv6 link-local (`fe80::/10`). That is the whole of what an operator is in a position to vouch for, and the LAN bind above is the case it exists for. Anywhere rule 1 already admits plaintext the key changes nothing at all. The address weighed is the **listener's own**, read once at bind time and never guessed per connection from where a peer claims to be — so none of this bounds who may connect. A listener on `192.168.1.20` with the key set answers anything that can route a packet to it, and the credential that admits a phone crosses that network readable, so whatever can watch those bytes has it too — and what it then has is everything a stolen phone token has: the whole event log and the approval path. **Not the terminal.** A connection admitted by this key is advertised `terminal_pty: false` and its `terminal_attach` is refused `not_authorised`, because vouching for a network is a different statement from the bytes on it being unreadable, and a live shell's keystrokes are not something this daemon sends in the clear. The terminal it replaced was encrypted and TOFU-pinned in every configuration there was.
3. **It is refused on the wildcard address and on a public one.** `0.0.0.0` and `::` put the bearer token on every interface this Mac has, including the ones nobody can enumerate in advance; plaintext on a public address is private on no hop of the way. Set on either, the key is logged as refused and the listener still serves TLS or nothing. An address the daemon could not check against its own tailnet — because `tailscale ip` did not answer in time — is never called public: unasked, it is refused and told to restart rather than to move, since it may be the tailnet address the operator meant. With the key set that outcome survives for the IPv4 half of a tailnet and not the IPv6 half, because Tailscale allocates IPv4 out of `100.64.0.0/10`, which rule 2 does not cover, and IPv6 out of `fd7a:115c:a1e0::/48`, which sits inside the `fc00::/7` rule 2 does. So an unconfirmed Tailscale IPv6 bind is honoured and serves plaintext — on the operator's word, not on anything this daemon confirmed.
4. **`tls_required` wins.** It is the stronger, opposite statement, and the opt-in never quietly undoes it: honouring an exception to it would announce plaintext the admission gate then refuses.
