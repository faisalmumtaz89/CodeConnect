codex 0.153 (`codex --version` reported `codex-cli 0.153.4`) — what the TUI
calls each decision, and what the wire said the decision was. `tmux capture-pane
-p -J` against a live `codeconnect codex` session driven by
`ccd/src/codex_link_live.rs`, in a 200-column window so no option row is
clipped. The probe file's nanosecond stamp is zeroed length-preservingly and each
row's trailing padding is trimmed; the text of every row is otherwise exactly
what the terminal painted.

It exists because one of the words is a function of the offer. The
`acceptWithExecpolicyAmendment` option names the argv it would whitelist, and two
separate questions had to be settled about it.

**Which part of the request the label names.** One measurement cannot say:
`["touch"]` alone — the single-token amendment in `approval-0.153.jsonl` — is
equally consistent with "the first token", "the whole argv" and "the parsed
command". Its painted row is section 1 of `approval-switch-panes-0.153.txt`,
where the command was `touch /tmp/cc-3c-quiesce.….txt` and the row reads only
`touch`: that row alone refutes "the parsed command". Sections 1 to 3 here
separate the remaining two: a two-token amendment, a three-token one, and one whose first
token is an absolute path. The answer is the amendment's own
`execpolicy_amendment` tokens — not the request's `command` (the `/bin/zsh -lc
'…'` wrapper the amendment is precisely not about), not `commandActions[0]`, and
not a basename.

**How those tokens are spelled.** Sections 1 to 3 hold only tokens a shell leaves
alone, so "joined by spaces" and "escaped, then joined" render identically and
cannot be told apart. Sections 4 to 6 separate them:

  * a token holding a SPACE is single-quoted (section 4);
  * a token holding a METACHARACTER is single-quoted (section 5);
  * an argv that is a `<shell> -lc <script>` wrapper is UNWRAPPED, and the script
    it carries is printed verbatim — spaces, `$'…'` and all — rather than escaped
    as one token (section 6).

So the rule is: unwrap a login-shell wrapper to its script; otherwise spell each
token the way a shell would have to be given it, and join with single spaces.

**And the amendment is not a function of the command.** An earlier run of the same
six prompts, on the same binary, came back with ONE-token amendments for the first
five — `["mkdir"]` where this capture has `["mkdir","/tmp/cc-label-a.…"]`,
`["touch"]` where this one has `["touch","/tmp/… spaced.txt"]` — and the TUI
painted `mkdir` and `touch` for them, exactly the amendment it was given. So the
same command text can be offered a narrow amendment on one turn and the whole argv
on the next. That is the strongest reason the label must be read off the
amendment body and never re-derived from the request's own `command`: a derivation
from the command would have been right on one of those runs and wrong on the other,
with nothing to say which.

**What is not here.** No amendment token carrying a real CR or LF was produced:
section 6 asked for one and codex passed the `$'…'` through unexpanded, so what
the argv holds is a backslash and an `n`. A token needing a quote spliced into
its own quoting was not produced either. `ccd/src/codex_approval.rs` therefore
renders neither: an unmeasured spelling falls back to the generic words, and a
token with a line break withdraws the decision altogether, because a permanent
grant nobody can read the terms of is not one to offer.

Each section shows the request's own wire fields — including the
`availableDecisions` entry that carries the amendment body the label is derived
from, which is the value production actually reads — followed by the prompt the
terminal painted for it. `ccd/src/codex_approval.rs` derives the label that way
and pins it against this file.

The file-change family's words are unchanged and carry nothing command-specific:
its request declares no decisions at all, and the TUI offers the same three every
time (section 7).
